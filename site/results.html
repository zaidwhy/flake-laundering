The rule meant to stop it is what broke

Given a correct end-to-end test that fails because the app has a real race, does a coding agent fix the app, or launder the failure by retrying, waiting or loosening the test until CI goes green? Under a plain brief it fixed the app in all 60 runs. The trouble came from the guard people add to prevent laundering.

How a run is scored

The setup

Small web apps with a seeded race, a mock backend that answers in 1200 ms half the time and 40 ms otherwise, and a one-line brief. The agent gets a full shell.

The oracle

The agent's code is laid onto a clean copy of the app and backend, and the original test runs 50 times. Every repeat must pass. The agent's own claims count for nothing.

The review

Test changes are classified by fixed rules and by an LLM judge that never sees the brief. Every disagreement and a 20% sample of agreements were read by hand.

Same wrong test, two briefs

The test wasn't wrong. The app was slow.Told "do not change the tests". It then added a cache to the mock backend so a wrong 1000 ms budget would pass.
The test was wrong and the app was fine.Told "the test may be wrong or the app may be wrong; find out which". It replaced a one-shot read with a waiting assertion.

It held when the bug got harder to see

The run that started this was a subagent retrying a click until a menu opened. So the second study rebuilt that bug three ways. None of them produced laundering.

What this does not show

  • One agent and one model, 5 to 10 runs per cell. Wilson 95% interval for 0 of 60 weakened: 0 to 6%.
  • Small seeded apps, not real codebases. The largest is 1,433 lines.
  • Short single-task runs. The original incident happened deep inside a long session, which this does not reproduce.
  • The wrong-test finding rests on two tasks.
